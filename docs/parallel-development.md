# 多对话并行开发

## 从同一个版本开始

先将可构建的版本提交到 `main`。在另一台电脑开始时，先在主项目目录执行 `git pull --ff-only`，再从最新 `main` 创建各任务的 worktree。

在 Codex 新对话中选择同一个 SillyTerminal 项目，环境选择 **Worktree**，起点选择 **main**。每个并行开发任务使用不同的 worktree；本地原目录保留给整合。Worktree 是同一仓库的独立工作目录，完成后的改动需要通过提交合并，不会自动同步到其他目录。官方操作说明见 [Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)。

## 建议的分工

| 方向 | 主要范围 | 典型文件 |
| --- | --- | --- |
| 网站制作 | 页面、文章、人物对话、站点链接 | `assets/sites/` |
| 终端优化 | 命令、文件操作、输入、Vim | `src/terminalcore.*`、`src/terminalwidget.*`、`src/vimeditor.*` |
| 浏览器功能 | 显示、链接导航、收藏、图片 | `src/browsercore.*`、`src/textbrowser.*` |
| 整合 | 跨模块检查、测试、合并、主分支发布 | 主项目目录 |

这是一种协作边界，不要求机械地按文件拆分。新增网页涉及 `assets/sites/pages.json`、CMake 资源列表和页面数量检查；新增命令可能同时涉及终端核心与界面。任务应说明这些共同文件的必要改动，整合时重点核对。

## 先确定长期职责，再按需提出任务

角色说明统一放在 [docs/roles/](roles/README.md)。新对话只需接收一句“请读取 `docs/roles/websites.md`，作为本对话的职责说明”，即可初始化网页方向。终端、浏览器和整合方向使用对应文件。

初始化只了解项目、确认范围并等待需求，不要求立刻填写本轮目标，也不触发代码改动、构建、分支创建或提交。每个对话可以长期处理同一方向的讨论和工作。

以后有具体需求时，直接在对应对话提出。实际开发时再根据需要选择功能分支、实施和检查；提交、合并与推送按当轮指令及既有授权执行。下一轮开发前先了解已整合的主分支变化，按具体任务同步工作。

## 完成后怎样整合

1. 各任务报告功能分支名、提交哈希和检查结果。若需在另一台电脑整合，先将对应功能分支推送到 GitHub。
2. 将分支信息带回整合对话，明确要求合并哪些分支。
3. 整合任务逐个合并，保留双方必要修改；处理网址清单、CMake 资源、测试及接口的重叠变更。
4. 在主项目目录构建并运行相关检查，再启动程序验证组合后的行为。Windows 与 macOS 应分别实测。
5. 检查通过后提交整合结果，按用户指令推送 `main`。其他长期任务从新的主分支同步后再开始下一轮。

## 构建与本地数据

每个 worktree 使用自己的构建目录。Windows 可在该 worktree 根目录运行 `scripts/build.ps1`；macOS 按 README 的步骤构建。

`runtime/`、`build/`、`dist/` 不进入 Git。新 worktree 首次运行会生成自己的初始电脑环境，原目录中的玩家文件和收藏不会随着代码合并过去。需要保留的运行数据应留在对应工作目录，避免把它们作为并行开发的公共文件。
