# 固定家庭摄像头设计草案

## 状态与范围

用户已确认：下一台可连接的设备为家庭摄像头，先设计固定机位；未来通过 ComfyUI 生成图片；仅在玩家明确要求拍照时触发生成。DeepSeek 参与提示词整理是候选方案。

本文其余设备细节、状态规则和接口分工均为设计建议，供后续讨论与实现。本轮仅编写设计，当前代码尚未实现摄像头、场景状态、图片查看或外部 API 接入。

## 设备与玩家体验

建议以一台安装在客厅角落、略向下俯视的固定网络摄像头作为第一台设备。视角、焦距和画幅固定。设备名称、型号、地址、账户来源和网络可达方式另行确定。

建议的首期操作为连接、身份验证、查看设备状态、拍照、查看和保存已经拍摄的图片。系统级登录、音频、录像回放及其他控制功能按后续需求设计。

连接后显示设备身份、连接状态及可用操作。明确执行拍照后才创建拍摄请求；查看设备信息、重新连接和打开旧照片均不自动拍照。首期展示按需取得的静态照片。

拍照权限由目标设备账户与服务规则决定。设备离线、未通过认证或没有拍照权限时，在生成之前返回对应的访问结果。图片生成服务故障应表现为本次拍照未完成，设备的网络状态保持由目标状态决定。

## 场景如何确定

系统保存一份明确的场景定义，以及在世界时间中发生的状态变化。拍照会观察当时的状态；拍照动作本身不随机决定谁出现、门是否打开或物品是否存在。

| 内容 | 示例 | 决定方式 |
| --- | --- | --- |
| 固定构图 | 镜头左侧是窗，中央是沙发，右侧是房门，近处是茶几 | 预设场景与参考图 |
| 稳定外观 | 墙面颜色、沙发样式、家具比例 | 固定素材与视觉描述 |
| 可变状态 | 房门开关、灯光、窗帘、物品位置 | 世界状态与明确事件 |
| 人物 | 是否在场、位于哪里、正在做什么 | 已定义的人物状态或事件 |
| 可见范围 | 人物是否出画、物品是否被遮挡 | 固定视野和预先设计的可见性规则 |
| 成像效果 | 暗处噪点、轻微压缩感 | 视觉规则，可允许不影响事实的变化 |

固定机位允许用画面区域与遮挡关系描述首个场景，例如“房门打开时遮住右侧墙面的一部分”。复杂人物走动或遮挡应先补全相应规则，再作为可见状态加入。

采用世界时间记录拍摄时刻。世界时钟是否随现实时间推进、退出期间是否推进，尚待单独确定。无论以后选择哪种规则，生成耗时都不能改变一次请求已冻结的拍摄时刻与场景内容。

## 一次拍照的流程

1. 玩家明确执行拍照，系统检查目标是否可达、身份和拍照权限。
2. 为本次拍摄建立唯一记录，冻结拍摄时刻、场景版本、设备成像设置和可见事实。
3. 从固定场景定义与冻结的状态整理出画面描述；可选择调用 DeepSeek 编写提示词。
4. 检查返回字段、场景引用和允许的描述范围，将提示词及参考素材填入已选定的 ComfyUI 工作流。
5. 提交生成任务，记录任务标识，等待或查询结果。
6. 取得图片后，将其保存并关联到本次拍摄记录，再向玩家显示。

界面可使用拍照处理中、完成、失败等反馈。处理中重复操作应能识别同一请求，避免意外重复提交；玩家之后再次明确拍照才创建新的拍摄记录。

生成失败后的重试沿用该记录冻结的状态。即使等待期间人物已经离开，重试仍生成原拍摄时刻的画面。已完成照片再次打开时读取保存的原图。

## DeepSeek 与 ComfyUI 的分工

程序负责设备访问规则、世界状态、可见性和拍摄记录。DeepSeek 负责将提供的可见事实整理成适合已选图像模型的描述，ComfyUI 执行图像工作流。

发送给 DeepSeek 的上下文包括：固定机位描述、固定外观、可见人物与物品、光照和门窗状态，以及不得改变的场景约束。设备密码和镜头外的剧情信息不属于这份上下文。

可让 DeepSeek 以 JSON 返回本次拍摄标识、画面描述和所使用的事实标识。程序检查字段、标识和约束；结构化格式本身不能证明自然语言描述或最终图片符合事实。固定场景约束由程序保留，模型输出不写回世界状态。

对这种固定机位，规则模板也可以完成状态到提示词的转换。提示词整理保留统一输入输出，允许后续比较模板和 DeepSeek 的实际效果。

ComfyUI 接收的是一个填好参数的工作流。具体模型、参考图输入、采样参数以及是否使用独立的负面提示词字段，应随工作流选型确定。程序保存所使用的场景、提示词和工作流版本，便于检查生成结果。

## 示例：同一房间的一次拍摄

以下仅说明数据流，不代表已确定剧情：

- 固定场景：客厅角落的宽幅固定机位，左窗、中央沙发、右房门、近处茶几。
- 拍摄状态：房门关闭，落地灯开启，窗帘拉上，画面内无人，茶几上有一只蓝色杯子。
- 提示词内容：从上述固定机位拍摄的家用监控照片，保持参考图家具位置和外观，表现指定灯光、门窗与物品状态。
- 约束：保持机位与构图；人物数量为零；杯子位于茶几；不增加剧情物品或可读文字。

之后只有明确的世界事件才能改变这些事实。DeepSeek 不能为了画面丰富自行增加来访者、纸条或其他线索。

## 固定画面的连续性

固定机位缩小了视角问题，但每张图独立文生图仍可能改变家具、构图和人物外观。建议为场景准备一张经过检查的基准图，按所选工作流加入参考图、局部编辑或深度、边缘等约束；这些方法的实际稳定程度需要用连续拍摄样本验证。

文字、数字、物品数量和人物身份如果承担线索，应使用固定素材、独立合成或经过检查的输出保证可辨认。提示词及固定随机种子均不足以保证这些细节始终正确。记录中的拍摄时间和设备标识由程序显示或叠加。

## 持久化与故障

预设场景、固定外观与参考素材按资源规则管理。玩家运行中的场景状态、拍摄记录和生成图片保存在被 Git 忽略的运行数据中；具体目录和版本迁移方式在实现时确定。

拍摄记录至少关联拍摄标识、世界时间、冻结的可见状态、场景版本、提示词、生成任务状态以及保存后的图片位置。ComfyUI 自身的队列与历史不能替代项目的持久化记录。

DeepSeek 不可用时，可按实现时确定的规则使用固定模板或返回失败；ComfyUI 不可用时保留失败记录，允许重试。不用旧照片冒充本次拍摄结果。启动后可恢复查看已完成照片，未完成任务的恢复或重试应使用原拍摄状态。

## 后续待确定

- 摄像头如何被发现、从玩家网络如何可达，以及账户与权限的来源。
- 房间的用途、具体布局、人物和事件；首期需要哪些可变状态。
- 世界时间推进方式，以及人物事件如何持续存在。
- ComfyUI 的部署、模型、工作流、参考素材与生成等待时间。
- DeepSeek 是否接入、选用模型、描述格式和失败处理。
- 终端的拍照入口、图片查看与保存交互，及与浏览器方向的衔接。

## 设计依据

- [ComfyUI 官方服务接口](https://docs.comfy.org/development/comfyui-server/comms_routes)：工作流提交、任务队列、执行结果与图像获取。设计中的拍摄记录、权限及持久化由项目自行提供。
- [ComfyUI 官方深度控制示例](https://docs.comfy.org/tutorials/controlnet/depth-controlnet)：深度与轮廓等结构条件可以辅助约束构图，效果需要按选定模型与工作流验证。
- [DeepSeek 官方 JSON 输出说明](https://api-docs.deepseek.com/guides/json_mode/)：支持以 JSON 输出供程序解析；项目仍需处理空结果、格式与业务约束检查。
